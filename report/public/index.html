Read the noise before reading the numbers.

Two in-process runs of the same commit, on the same model, over the same three instances both scored 3 / 3 and differed by a third in cost: 1,071 s / 813 k against 690 s / 550 k. Nothing changed between them but the reporting code. A single instance is a coin flip — astropy-12907 has passed alone, failed in a slice, and passed twice since, all on the same commit.

Three instances measure that the loop runs. They do not measure how good it is, and no figure on this page should be read as a trend.

This run happened inside the deployment. The agent ran in the object with the instance’s own image mounted as its machine, the model calls went out through the production queue, the grader ran in the same container before the runner released it, and the container was never offered to the agent to destroy. The previous version of this table came from a Node process over an in-memory database; it is gone, and the only change in outcome is that 14182 resolves here and failed there. 13398 is the one instance that failed in both runs, and it is the over-reaching one: 785 s, sixty calls, three files. Every success landed in one to three files.

The object was billed for 73 % of wall clock — 2,105 s of 2,869, 165 s of it the runner grading. τ² bills the object for 3–5 %. Same substrate, opposite bill, and the difference is where the waiting happens: a model call leaves the object through the queue, a tool call runs inside it, and this task is 247 shell commands in a container. On the three instances that the in-process run and the earlier on-object slice share (object bench-swe1, same day, same branch: 3 / 3, 692 s, 75 % billed), wall clock is the same as in-process (692 s against 690 s): the cost moved onto a different meter, not onto more time. This is a property of what ships, measured, not something this change fixes.

96 % of prompt tokens came from cache, so the gross figure overstates the bill by more than twenty times — of 5.2 M, roughly 204 k were actually re-read. A cache rate is still not a cost measure on its own: the failed instance re-read the most at 98 % cached. The container is alive for 92–100 % of wall clock; whether stopping it between calls pays still depends on run9’s compute-versus-storage rates, which we do not have. run_js was not used once in 247 tool calls; the two run calls are run9’s JavaScript inside the container, not the sandbox.

τ²-bench retail

does it follow a written policy while a person changes their mind · 8 tasks × 3 trials, inside a deployed Durable Object

The domain is a mounted plugin, the customer is a second model, and the score is the database — whether the agent left the world in the state the annotated solution leaves it in. The agent's own account of what it did is not evidence.

This run happened inside the deployment. The agent runs in the object, the model call goes out through the same queue production uses, and the transcript stays in the object afterwards. The earlier figures on this page came from a Node process driving the same loop over an in-memory database — a configuration nobody deploys, which also left nothing behind to read. Only the customer is still local, because τ²'s user is a second model with no access to the domain.

Five on-object runs of the same benchmark and model, and the first thing to publish is that they disagree — pass^1 from 62.5 % to 87.5 %, and not in the order you would guess. Eight tasks × three trials each, on deepseek-flash, in a deployed object. The disagreement is the finding: one run cannot say how good the loop is.

Two metrics, and they are not the same number. pass^k counts tasks that pass k trials in a row (out of 8); the trial count is the raw score over all 24 attempts. The page reports pass^k — it is the one a deployment cares about — and gives the trial count alongside, because they can differ by ten points in the same run.

B is a labelled line, not a checkable row. Its aggregate is in a commit message; its task numbers (1, 5, 6 in trial one) exist only in the page text that commit wrote, from a log nobody kept, and the object holds no archived task for it. A run whose vector cannot be re-derived is recorded and marked, not promoted to a peer of the runs that can be. C, D, E, F and G carry full evidence and their per-task vectors are below; the logs for the first four are in report/runs/2026-09-10, the records of F and G are in report/runs/2026-09-11, and their transcripts live in the objects, read back through /bench/trajectory.

Run F is the one that changed the plugin, not the loop. It is the same benchmark, model and object, with the plugin defects fixed (8ae6754, on the grader already fixed at c7aa888) that the other runs were measured with: the tools now carry upstream's parameter descriptions verbatim, so an order id that needs a leading # says so; and calculate evaluates with a parser rather than new Function, which the object runtime forbids. The effect is visible and bounded: zero tool errors across all 24 trials, where the three preceding runs produced 29 Order not found errors and 8 calculate failures between them — and the fix landed on the tasks that had the errors, not on the ones that did not. calculate went from never working on the object to being called twice and succeeding twice, which is a capability appearing rather than an error count falling.

What that did not do is raise the score, and the page should not be read otherwise. Run F's pass^1 over tasks is 75 % (17/24 trials), below run E's 87.5 % on the same metric. That is not a regression: the runs fail on different tasks, and no two of the five share a failing task. The defects cost turns inside counted runs — 37 wasted calls, and the rounds they consumed — and removing them removed the waste. A fix that makes the harness faithful to the benchmark is not a fix that makes the agent better at it, and reporting one as the other is how a benchmark report flatters itself.

A grader bug was found, mid-sequence, and fixed. In D, task 2 failed all three trials with the database in the gold state: the agent returned the right three items in a different order, and the check compared the list positionally. The domain sorts that list when it applies the write — the field is a set — so the action was right and the check was wrong. Fixed in c7aa888 (which runs on the driver, so it needed no deploy). D printed 19/24 and stays printed; E is the next run under the fixed grader, and it shows zero ordering-artifact failures. Note what the fix did not do: it did not recover task 2's three points, because the agent does not repeat itself — E simply lost different trials. A corrected grader changes which trials fail; it does not add a fixed number of passes.

The runs disagree on the aggregate and on the shape. No two of C, D, E and F share a failing task, and their pass^1 spans 62.5 % to 87.5 % — wider than any loop difference the page could claim, and wider than the gap between the old and fixed graders. Their pass^3 spans 37.5 % to 75 %, so the runs disagree about which metric tells the story too: E is best on pass^1 and near-worst on pass^3. G, the first run on the revised core prompt, is the best aggregate so far on every metric — and by the page’s own argument one run cannot attribute that to the prompt: its three failures are tasks 1 and 5, which F also failed, and the spread between runs on the same code is wider than the step from F to G.

What the remaining zeros are. Every failed trial in every run ends on the simulated customer, never on a tool or the substrate: no call was lost, no run stalled, no object failed to wake. In run F the endings are a customer holding off over a question the domain has no tool for, quitting after one turn, and hanging up on a confirmation (“shall I proceed?”) rather than answering it. This is the benchmark's own behaviour, and it is the reason the page reports the failures rather than the harness scoring around them.

Six of run F’s seven failures are one shape: the agent investigated and wrote nothing. Every one is an event-modifying request — an exchange, a return, a modification — and every one ends on the customer, not on a tool. The trial that wrote the wrong thing (an exchange where a return was asked for) is the seventh. This is not a tooling failure: run F has zero tool errors, so the agent had working tools and did not reach for them, which is the sharpest way to state it. And it is not a defect either: τ²’s own policy requires the agent to list the details and obtain an explicit yes before any write (policy.md L16), so four of those conversations are the agent following the benchmark and a simulated customer hanging up mid-answer. Making them pass would mean writing without confirmation. That rule belongs to the benchmark, not to antiproton. The harness imposes no permission step of its own — an absent mount policy allows the write — and the plugin carries one because the benchmark’s company does. A plugin can still configure approval, which is the next point.

Reading the trajectories rather than the scores turned up three product notes, which are not the same as the zeros. None is a change to a published number, and each is stated with its status so it is not read as a defect where it is a choice.

A real bug, and a prompt fix that measured as no fix. In three of run F’s conversations the agent told the customer a refund would arrive “in 5–7 business days” — once “per the card refund timeline”. The policy grants that timeline for cancellations and payment changes only (policy.md L92, L106); returns and exchanges say the customer gets an email (L126, L136), and no tool result contains the number. A sentence was added to the core prompt — state timelines, fees and procedures only when a tool result or the policy backs them — deployed, and measured in run G: four conversations say it (any “business days” phrasing, counted per conversation), one of them “per our policy”. The sentence did not take, and the reason is visible in the transcripts: the number is in the policy the agent holds, two sections away, and the agent reads that as backing. What would fix it is grounding to the section that governs the action, not a general instruction to be grounded; that is a change to how a policy is presented to the agent, recorded here rather than tuned for a benchmark whose policy is not ours.

Permission, measured on the same run. The same prompt change tells the agent not to ask for permission it already has. Run F asked the customer 21 questions and run G 26; every one, read in place, is either the confirmation τ²’s policy requires before a write or a choice only the customer can make — which variant, which card. There were no unneeded permission requests in F to remove, and G added none. Zero tool errors in both runs; G billed the object for 28 s of its 1,004 s wall (3 %).

A design item, recorded rather than patched. The harness asks nothing of the customer by default; a plugin can configure approval, and when it does, the operation is held with no visible pending marker and no expiry. In the product a conversation resumes on the customer’s next message, so this is not a dead end; what is missing is any marker that an action is waiting for a decision. The gateway’s approvals table records tool-level approvals, not “an operation is held and waiting”. So the question is narrower than “should the agent ask?” — under a default of not asking, it is whether an approval-gated mount should show a pending state and whether it times out.

A presentation limitation. The agent inlines raw identifiers — 250 table rows and 254 raw identifiers across 24 conversations — 163 item ids (about seven a conversation) and 91 order ids — because the policy — τ²’s, as above — requires listing the exact details before a write and there is no other way to present a choice. The content is correct; the affordance is missing.

Kept as-is, deliberately. Offering a human transfer when the customer asks for a return label or a payment link the domain has no tool for is correct escalation, not a gap to close. Saying “let me look that up” while calling a tool costs a turn the benchmark counts and reads as progress to a person; 44 of the run’s 196 model turns carried a message to the customer alongside a tool call. And accepting order ids without the leading # would make this plugin present an easier task than the published one — a way to raise the score by measuring something the benchmark never asked for.

One correction on the endings, because the page once implied otherwise. The transcripts all end on the agent’s turn — but not because the episode was cut. The runner posts a customer message to the object only when it is not the simulator’s stop signal, so the final ###STOP###/###TRANSFER### is consumed by the loop and never archived. Zero episodes ended by turn exhaustion in any run; every ending is the customer stopping or transferring. So the missing final turn is an artifact of the protocol, and the zeros are the customer’s, not an ambiguity in the harness.

The page's own first version had this wrong. Its headline read "pass^1 87.5 % · 21/24" — the trial count in the pass^1 slot, since 21/24 is 87.5 % and pass^1 over tasks is 62.5 %. The conflation predates this table and is corrected here for every run, which is why the /24 column stays: it is the number a reader would otherwise assume is pass^1.

pass^k is the number that matters. pass^1 asks how often this works; pass^3 asks whether the same task survives three attempts, which is the question a deployment actually has. Reporting only the first is how a benchmark flatters a loop. It is reported here as a summary under the vectors, not as the lede.

run_js went unused on the object, in two independent runs. The page once said no benchmark had ever triggered the sandbox; that was true of SWE-bench and unproven for τ². The tally has now printed for τ² twice — 24 trials each, no run_js — so the twice the page used to cite is in-process only, and the sandbox is not shown to have a shape of problem here. That claim would need an on-object run that reaches for it.

What the zeros were. In C: task 2 ended in the benchmark's own user simulator quitting on the first turn (that task's instructions are a single full stop), task 5 the agent returned an item it should have exchanged, and tasks 6 and 7 it stopped short of the write. In D: task 2 is the grader bug above, task 5 the same return-vs-exchange mistake, self-corrected on the third trial. In E: task 5 fails every trial, three different ways — and four of its six zeros are the same shape as C's, a conversation that ends with no write at all, which is the failure mode the system prompt was rewritten to address.

E's failures are composed differently from C's. C has two tasks failing all three trials; E has one (task 5, failing three different ways) plus three single flips in tasks 1, 2 and 6. So E's pass^3 = 50 % rests on one near-deterministic task and three coins, not on two lost tasks — the pass^k column above cannot show that difference, which is why the vectors are the table.

E is also the run that proves the grader fix. It has zero db=ok act=NO rows — no action was ever rejected for the shape of its arguments — where D had three. Task 2, the grader artifact in D, passes in E's trials 1 and 3.

F’s zeros are the benchmark’s. It has no tool errors at all, so every one of its seven failed trials ends on the simulated customer rather than on a tool. Four are the customer stopping over something the domain cannot answer or confirm — a Google Home question, a payment link with no tool behind it — or quitting one conversation after a single 18-second turn. Two are the customer ending the call on a “shall I proceed?” rather than answering it. One is the exchange-then-return divergence executed rather than declined. And task 5, which failed every trial in all three earlier runs, completed its write here for the first time in any run — once in three. That is a flip, not a fix, and it is the honest description of what changed.

Every figure names its run, and the run names its object. B has a source but no evidence and is marked as such; C, D, E, F and G have both. A sixth matrix from the same session is not shown at all: it ran in process, before the on-object runner existed, so it does not belong in this table. It is, however, the only run that ever used run_js.

What the object was billed for

the number the in-process runner could not produce · measured over the same 24 tasks

Cloudflare bills a Durable Object for the wall clock during which it is active, with no exemption for waiting on the network. So the question is not how long the run took but how much of that the object was awake for — and a completion is almost entirely waiting.

37.1 sobject active
436 sspent in the provider
168 msobject time per model call

The 436 seconds of provider latency are billed as Workers CPU in the queue consumer, not as object duration — which is the whole reason the model call leaves the object. The remaining wall clock is the benchmark's own customer simulator, running here.

Two things were paid for and did not need to be. The alarm rearmed on the deferred handle's poll interval, one second, so it woke roughly five times per model call to ask whether an answer had arrived — an answer the queue delivers and wakes the object for. And the sweep that re-sends unanswered jobs could not tell never sent from still running, so it re-sent calls that were in flight: one conversation dispatched eleven calls fifty-one times, and a duplicate is not free, because a second worker asks the provider again and the losing answer's tokens are billed the same.

SWE-bench Verified

answered · 10 instances · inside the deployed object

Whether the loop can carry a multi-turn task on a real machine to a graded result. 9 / 10 on the deployed model, measured in the deployed object with the grader in the agent’s container. Ten instances is a sample, not a submission.

pi storage conformance

answered · 21 / 21, two backends

Not ours: createStorageConformance ships inside pi and runs unchanged on node:sqlite and on real Durable Object storage. It covers what our own tests would not, because ours encode our own assumptions — mixed-write atomicity, rollback across four tables, cursor before limit, admission order under concurrent commits. A contract, not a benchmark.

Substrate probes

answered · on real infrastructure

Measured on Cloudflare rather than read from documentation. The load-bearing one: a Durable Object is billed for wall clock with no exemption for network I/O, and a completion is ~94 % waiting. That single fact is why the model call leaves the object — 40.8 s billed against 709.2 s waited over 79 calls.

AppWorld — credential custody

a property, not a score · needs a licensed install

9 apps, 457 APIs, 362 of them (79 %) behind an access token. Nine end-to-end cases assert that no schema mentions access_token, the credential-reading tool is not mounted, an authenticated call succeeds without the agent ever logging in, and the token never appears in a tool result. It measures what the model cannot see, so there is no pass rate to report.
