Read the noise before reading the numbers.

Two runs of the same commit, on the same model, over the same three instances both scored 3 / 3 and differed by a third in cost: 1,071 s / 813 k against 690 s / 550 k. Nothing changed between them but the reporting code. A single instance is a coin flip — astropy-12907 has passed alone, failed in a slice, and passed twice since, all on the same commit.

Three instances measure that the loop runs. They do not measure how good it is, and no figure on this page should be read as a trend.

SWE-bench Verified

does the loop work a real problem end to end · 3 astropy instances, official scoring

The only benchmark here that needs a real machine: a repository, its dependencies and its test suite. The agent gets one through the run9 mount, which is deliberately the only way it can — the sandbox it normally works in has no filesystem and no network. Scoring is SWE-bench’s own: apply the official test patch, require the failing tests to pass and the passing ones to still pass. The agent’s claim to have fixed something is not evidence.

Only runs 1 and 3 compare loops — same model, one variable, 1 / 3 to 2 / 3. The score is not the interesting part of that. Both instances the old loop failed ended after a single model call: the model never got to attempt the task, the loop simply stopped. That was the failure mode six rounds of patches in the old harness had been papering over, and it is why the token cost rose — the new loop is doing work the old one was not.

94 % of prompt tokens came from the provider’s cache. Reporting the gross figure overstates the bill by more than ten times — of 549,815 tokens, roughly 33,000 were actually re-read. An append-only transcript is what earns it: a turn adds to the tail and leaves the prefix untouched, which is the shape a cache rewards. Every token figure recorded before run 5 is a gross number.

run_js was used zero times, across three instances and 53 tool calls. The sandbox is offered on every turn and the agent never reached for it. The honest reading is not that it is useless: this task is shell work inside a container, and run_js earns its place by replacing several calls with one. It says this benchmark does not test it, and nothing here says whether it pays elsewhere.

Everything measured, and what it measures

grouped by the question each one answers

SWE-bench Verified

answered · 3 instances · 5 runs

Whether the loop can carry a multi-turn task on a real machine to a graded result. Currently 3 / 3 on the deployed model. Three instances is a sample, not a submission.

pi storage conformance

answered · 21 / 21, two backends

Not ours: createStorageConformance ships inside pi and runs unchanged on node:sqlite and on real Durable Object storage. It covers what our own tests would not, because ours encode our own assumptions — mixed-write atomicity, rollback across four tables, cursor before limit, admission order under concurrent commits. A contract, not a benchmark.

Substrate probes

answered · on real infrastructure

Measured on Cloudflare rather than read from documentation. The load-bearing one: a Durable Object is billed for wall clock with no exemption for network I/O, and a completion is ~94 % waiting. That single fact is why the model call leaves the object — 40.8 s billed against 709.2 s waited over 79 calls.

AppWorld — credential custody

a property, not a score · needs a licensed install

9 apps, 457 APIs, 362 of them (79 %) behind an access token. Nine end-to-end cases assert that no schema mentions access_token, the credential-reading tool is not mounted, an authenticated call succeeds without the agent ever logging in, and the token never appears in a tool result. It measures what the model cannot see, so there is no pass rate to report.

τ²-bench

not run on this loop

Tool calling under a domain policy. The only figure this project ever recorded — 8 / 8 vs 7 / 8 vs 5 / 8 over 8 tasks — compared the old harnesses and survives only in a code comment. The driver has been deleted rather than left broken, and nothing on this page says how the current loop behaves under a policy.
