The loop is pi’s now

The agent loop was replaced with pi’s harness and the machinery it replaced was deleted. This is what the thing is, what has been verified, and what is still open.

deployed antiproton.botiverse.dev model deepseek-flash upstream pi-agent-core 0.85.1 branch pi-storage · PR #1

Cloudflare bills a Durable Object for wall clock, with no exemption for time spent awaiting network I/O. A model completion is roughly 94 % waiting.

That single fact decides the architecture. The model call has to leave the object, which is why the queue exists and why it stayed. pi’s drive() calls the model itself — the two look incompatible until you notice pi already has a protocol for work it is not doing: answer stopReason: "deferred" with a durable handle, suspend, come back for it. It was built for provider batch APIs. Here the thing holding the work is our queue, and the harness cannot tell.

Who owns what

the split the system already ran on; pi’s API is cut along the same lines

the objectState and order. One Durable Object per (tenant, agent), its SQLite object-local.
the alarmTime. It calls step() once and comes back when drive() said to.
the queueWork in flight. It holds the model call so the object is not billed for the wait.
the workerWaiting. Billed for CPU, and awaiting I/O costs none.

accept() is a pure write: a person’s message is durable before anything is answered. drive() is the pass that does I/O, and it returns waiting rather than blocking. Nothing needs a lease or a fencing token — a Durable Object is single-threaded and pi’s mutation line serialises the writes, so there was never a second writer for them to protect against.

The transcript is the state now. A step used to rewrite the whole conversation as one JSON blob; one harness put a 447-tool catalogue in it and rewrote 211 KB of unchanging text per step. An entry is a row, and a step writes one.

What we depend on, by how it fails

pi is pre-1.0 · the pin is exact · docs/pi-upstream.md

Imported symbols

fails at the build

Four entry points: the package root, harness/session, harness/context, and harness/session/testing for tests, plus pi-ai for the provider contract. If one moves, nothing compiles.

Copied source

fails silently

Two pieces, both re-diffed on every upgrade because neither would fail to compile:

  • emptyUsage / addUsage, from a module pi’s export map does not publish.
  • Scan, cursor and stop-order semantics, written against pi’s in-memory reference.

Behavioural contracts

fails silently, and worst

Nothing imports these. Nothing types them. Everything rests on them — so each one now has a test, and an upgrade that changes one fails here rather than on a tenant.

  • drive() returns rather than blocks on a deferred response. This is the cost model.
  • A not-ready fetchDeferred answers with the same handle.
  • The inbox drains at accept() — not on a timer, not on drive().
  • create() starts no timers and reports what the last process left open. This is the whole of crash recovery; there is no sweeper any more.
  • Storage.commit is all-or-nothing across entries, values, lists and usage.

What is verified

contract, then behaviour, then quality — each can hold while the next fails

The storage contract is not ours. createStorageConformance ships inside pi as runner-independent cases, and all 21 run unchanged on node:sqlite and on real Durable Object storage. They cover what our own tests would not have, because our own tests encode our own assumptions: mixed-write atomicity, rollback across four tables, cursor before limit, admission order under concurrent commits, and a close that seals admission while still draining what it admitted. That last one failed first — the implementation re-checked the closed flag inside work it had already accepted, which is the opposite of the promise close makes.

The load-bearing loop cases are negative, because the properties that matter are things that must not happen: a pass never waits for a model, twenty passes while an answer is out add nothing to the transcript, and a run interrupted by eviction is reported open on the next open() and driven to completion.

Two figures matter more than the score.

The first is cache. Reporting prompt tokens alone overstates the bill by more than ten times: of 549,815 tokens, about 33,000 were actually re-read. An append-only transcript is what earns that — each turn adds to the tail and leaves the prefix untouched, which is exactly the shape a provider cache rewards. It was not measured until this run.

The second is zero run_js, across all three instances and 53 tool calls. The sandbox is offered every turn and the agent never reached for it. The honest reading is not that it is useless: this task is shell work inside a container, and run_js earns its place by replacing several calls with one. This benchmark is not the shape that tests it, and nothing here says whether it pays elsewhere.

Only the first two rows compare loops — one variable, same model. The third changes the model as well, and is here because it is what the deployment runs.

The score is not the interesting number either. Both instances the old loop failed ended after one model call: it was not the model failing the task, it was the loop stopping. The new one works them for ten to twenty-two turns.

A single instance is a coin flip. astropy-12907 has passed alone, failed in a slice, and passed twice since — all with the same code. Three instances measure that the loop runs, not how good it is.
